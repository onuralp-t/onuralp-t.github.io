§From "Hello WASM" to "How are you, WASM!?"

Check out my article for a WASM introductory text. In this article, we'll be moving on from "Hello WASM" to "How are you, WASM!?"

Or to state it more clearly: we'll look into how WASM works on a fundamental level.

§The WASM module

Before walking through how to include the WASM module into the web project, let's see what's inside the program that is going to be compiled into a WASM module in the first place.

// main.c
#include <stdint.h>

// JS-defined:
void wasm_log(const char *msg);

constexpr uint32_t SCREEN_WIDTH = 800u;
constexpr uint32_t SCREEN_HEIGHT = 600u;

struct {
  uint8_t pixels[SCREEN_WIDTH * SCREEN_HEIGHT * 4u];
} screen;

uint32_t screen_get_width(void)  { return SCREEN_WIDTH; }
uint32_t screen_get_height(void) { return SCREEN_HEIGHT; }
uint8_t* screen_get_pixels(void) { return screen.pixels; }
uint32_t screen_get_pixels_size(void) { return SCREEN_WIDTH * SCREEN_HEIGHT * 4u; }

void update(uint32_t frame_number) {
    for (uint32_t y = 0u; y < SCREEN_HEIGHT; y++)
    {
        for (uint32_t x = 0u; x < SCREEN_WIDTH; x++)
        {
            uint32_t idx = (y * SCREEN_WIDTH + x) * 4u;
            screen.pixels[idx + 0] = x + frame_number;
            screen.pixels[idx + 1] = y + frame_number;
            screen.pixels[idx + 2] = 150u;
            screen.pixels[idx + 3] = 255u;
        }
    }
    wasm_log("message from WASM update()!");
}

Built with:

clang --target=wasm32 ^
  -O2 ^
  -std=c23 ^
  -ffreestanding -nostdlib ^
  -Wl,--no-entry ^
  -Wl,--export-all ^
  -Wl,--allow-undefined ^
  -o main.wasm main.c

§Using JS functions from inside our WASM module

At the very top, we see:

void wasm_log(const char *msg);

This wasm_log function is only declared in main.c, not defined. Later, when we load the WASM module into our JS program, we'll define wasm_long inside JS. The -Wl,--allow-undefined CLI flag in our build command facilitates this.

§Accessing WASM variables from our JS script

constexpr uint32_t SCREEN_WIDTH = 800u;
constexpr uint32_t SCREEN_HEIGHT = 600u;

struct {
  uint8_t pixels[SCREEN_WIDTH * SCREEN_HEIGHT * 4u];
} screen;

First two constants are defined using C23's constexpr qualifier to have type-checked constants in global scope, as alternative to macros or enums.

When we do console.log(wasm.exports) later in our JS script, we will see screen but not our SCREEN_WIDTH and SCREEN_HEIGHT listed there.

The -Wl,--export-all flag in our build command facilitates the export of all functions and objects, but this doesn't apply to simple variables.

To solve this problem of not being able to access our variables from JS, we have few possible strategies in front of us. The first sensible option seems to be to pack our semantically related variables into a single struct (What I would do if I wasn't writing a WASM program).

§The Correct-looking Solution

If we have a struct like this (defined again in global scope):

#define WIDTH 800u
#define HEIGHT 600u
struct {
  uint32_t SCREEN_WIDTH;
  uint32_t SCREEN_HEIGHT;
  uint8_t pixels[WIDTH * HEIGHT * 4u];
} screen = {.SCREEN_WIDTH=WIDTH, .SCREEN_HEIGHT=HEIGHT};
  1. Later when we load the WASM module into our JS script, we will see screen listed in the exports list.
  2. There, we will get a pointer to the base of the screen struct.
  3. Then, we will have to walk through each element of the struct while being mindful of the memory layout of our struct (memory padding!) and how big every element is, manually calculating the offsets to each element and casting/viewing them as the correct type. This is perfectly possible, yet error-prone. Why don't we just let Clang calculate the memory addresses for us?

§The Correcter Solution

constexpr uint32_t SCREEN_WIDTH = 800u;
constexpr uint32_t SCREEN_HEIGHT = 600u;

struct {
  uint8_t pixels[SCREEN_WIDTH * SCREEN_HEIGHT * 4u];
} screen;

uint32_t screen_get_width(void)  { return SCREEN_WIDTH; }
uint32_t screen_get_height(void) { return SCREEN_HEIGHT; }
uint8_t* screen_get_pixels(void) { return screen.pixels; }
uint32_t screen_get_pixels_size(void) { return SCREEN_WIDTH * SCREEN_HEIGHT * 4u; }

Although getter functions get a bad rep, I think this is a good use case for them. Defining a getter function inside our WASM module offloads all the burden of memory calculations to the compiler, and gives us a human-readable and not-error-prone way of accessing our variables. These will most likely be used in the initialization part anyways, and they're not that bad even if they're used elsewhere.

We can also use fancy attributes to steer our compiler to optimize them in a nicer way like:

__attribute__((pure))
uint32_t screen_get_width(void)  { return SCREEN_WIDTH; }

The update function is relatively simple, it just does some animation, you don't have to comprehend it in a deep way.

§Inside JavaScript

const utf8_decoder = new TextDecoder("utf-8");
function wasm_log(c_str) {
	const str_start = c_str;
	let str_end = str_start;
	while (u8_view[str_end] !== 0) { // C's null terminated strings
		str_end++;
	}
    const message = utf8_decoder.decode(u8_view.slice(str_start, str_end));
    console.log(message);
}
  
  const wasm_compiled = await WebAssembly.instantiateStreaming(
    fetch("./main.wasm"),
    {
      env: { wasm_log }, // define what WASM module asks for
    },
);
    const wasm = wasm_compiled.instance;
    const we = wasm.exports;
    console.log("wasm.exports: ", we);

In the env element, we put in the implementation of the wasm_log function we call from inside our WASM module, and we create some helper variables like we which indexes all our WASM exports. To access our WASM exports, we use the strategy we talked about earlier:

function read_screen_from_wasm() {
	const screen_width = we.screen_get_width();
	const screen_height = we.screen_get_height();
	const screen_pixels = new Uint8ClampedArray(we.memory.buffer, we.screen_get_pixels(), screen_width * screen_height * 4);
	return { screen_width, screen_height, screen_pixels };
}
const { screen_width, screen_height, screen_pixels } = read_screen_from_wasm(we.screen);

We then resize our HTML canvas to the width/height we accessed from the WASM module:

	const canvas = document.getElementById("canvas");
	canvas.style.width = `${screen_width}px`;
	canvas.style.height = `${screen_height}px`;
	canvas.getContext("2d").scale(screen_width, screen_height);

After that, to write pixels to our canvas, we need to create a view into our screen_pixels array in the form of JavaScript's ImageData (we can only blit ImageData to canvas, we can't put screen_pixels to canvas directly):

const imageData = new ImageData(screen_pixels, screen_width, screen_height);

And for the grand finale, we define what is essentially a rendering loop. We create the equivalent of a while(true) loop that updates the WASM memory with WASM functions, and then uses a view onto the WASM memory to blit it to our HTML canvas, and then repeat:

	let frame = 0;
	function loop() {
    we.update(frame++); // update the screen_pixels data which lives in we.memory.buffer
    ctx.putImageData(imageData, 0, 0); // imageData is a view on screen_pixels which is in we.memory.buffer
    requestAnimationFrame(loop);
	}
	loop();

§Hello WASM, Hello SQLite, Hello everyone!

This article will describe the workings of this repo of mine, and what is necessary to serve a static website on Github Pages that uses SQLite's WASM build; moving the high-level explanation from code comments to, hopefully, where it makes more sense.

§Before we even start: CORS and WASM

To load in WASM binaries, you need to be in a cross origin isolated context. Usually this is not a problem, but because I use Github Pages to host the website in my repo, and because Github doesn't give users enough control to set these kinds of headers, we need to fix this CORS issue in another way.

We need COOP and COEP HTTP headers set like:

Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Opener-Policy: same-origin

Luckily, we're not the first one to encounter this problem, and there's this hack: https://github.com/gzuidhof/coi-serviceworker , thank you gzuidhof.

§What's going on in the main thread in index.html?

At the top, we have our message_types: the types of messages that we can send between our worker and main thread.

    const message_types = Object.freeze({
        MAIN_ENTER_TEXT: 0,
        MAIN_CLEAR_DB: 1,
        WORKER_DB_CONTENTS: 2,
    });

Currently, I manually define this struct in both main and the worker, which is kind of a stupid implementation, but I didn't want to create another common.js to include in both main and worker files, to keep things simple.

After creating the worker, we define when the main thread will send which messages to the worker thread, and with what payload.

    const worker = new Worker('my-sqlite-worker.js');

    user_input.addEventListener('keydown', e => {
        if (e.key === 'Enter' && user_input.value) {
        worker.postMessage({type: message_types.MAIN_ENTER_TEXT, payload: user_input.value});
        user_input.value = '';
        }
    });

    clear_db_button.addEventListener('click', e => {
        worker.postMessage({type: message_types.MAIN_CLEAR_DB, payload: 0});
    })

Then, we define how the main thread will handle incomming messages from the worker thread.

    worker.onmessage = e => {
        switch(e.data.type)
        {
            case message_types.WORKER_DB_CONTENTS:
            {
                let htmlstr = "";
                for (row of e.data.payload) {
                    htmlstr += `${row}<br>`;
                }
                db_contents.innerHTML = htmlstr;
            } break;
        }
    };

§What's going on in the worker thread?

In my-sqlite-worker.js, we start by including the JavaScript release of the SQLite library, and create the same message struct I talked about earlier:

importScripts("sqlite3.js");

const message_types = Object.freeze({
    MAIN_ENTER_TEXT: 0,
    MAIN_CLEAR_DB: 1,
    WORKER_DB_CONTENTS: 2,
});

To initialize the database, we do:

sqlite3InitModule().then(sqlite3 => {
    const db = new sqlite3.oo1.OpfsDb('/test.db');
    // ...
  • There are a couple of different ways of achieving persistence when using sqlite-wasm. To write to disk, this little program uses the OPFS (see: O stands for Origin).

We create the table, and then a helper function to query everything from the table and send it to the main thread through a message, and then call the helper to send the initial state to main:

db.exec('CREATE TABLE IF NOT EXISTS entries (text TEXT)');
const send_db_to_main = () => {
const db_contents = db.exec('SELECT * FROM entries', { returnValue: 'resultRows' });
    self.postMessage({type: message_types.WORKER_DB_CONTENTS, payload: db_contents});
};
    
send_db_to_main();

We then implement how we're gonna handle different messages that can come from main:

self.onmessage = e => {
    switch(e.data.type)
	{
    case message_types.MAIN_ENTER_TEXT:
        {
            db.exec({ sql: 'INSERT INTO entries (text) VALUES (?)', bind: [e.data.payload] });
            const rows = db.exec('SELECT * FROM entries', { returnValue: 'resultRows' });
            send_db_to_main();
        } break;

        case message_types.MAIN_CLEAR_DB:
        {
            db.exec({ sql: 'DELETE FROM entries' });
            send_db_to_main();
        } break;
    } // switch(e.data.type)
}; // self.onmessage
}); // sqlite3InitModule().then

§Bootstrap a VPS

§Choosing a Cloud Compute provider

Choose Oracle's free-tier VPS. They offer 1 vCPU, 1 GB RAM, 200 GB SSD and a public IP for free, though it's not static IP at free tier. This is enough to host a website for your personal project.

They also have an Always Free indicator that can assure you that you won't get charged if you stay in the always free tier. Account validation is a bit cumbersome as they ask for bunch of PII and also ask you to pay a nominal fee which they send you back as a way of identity verification.

  • Google Cloud Compute used to be my choice, but they recently stopped giving away free public IP's, so hosting small web servers on free-tier Google VPS's became no longer possible. Also not being able to put payment limits was always annoying.

§Meta settings for the Cloud Compute Provider

  • Network: As a general rule, you should start with only allowing network ingress/egress traffic to your VPS through standard HTTP(S) ports 80 and 443, and SSH traffic through port 22. You should set this up at the cloud-layer through your VPS's subnet settings, and we will set up these firewall rules inside the VPS itself as well.
  • SSH/keys: When setting up the network portion of your VPS in OCI, you get the option to have OCI make the SSH keys for you, and download the SSH keys to your machine. This allows you to connect to your VPS via your SSH keys, foregoing more insecure plaintext password authentication schemes. A small note, when you download the keys from OCI, you need to set up their permissions correctly.

§Inside the VPS

If you try to do a full system upgrade like sudo apt update -y && sudo apt upgrade -y, you will most likely stall to an almost complete stop and proceed very slowly because of the inadequacies of 1 GB of system RAM. Setting up swap memory and then update/upgrading is usually a solid first start.

§Setting up swap and Upgrading

Create 4GB of swap file, fix permissions, make swap, turn swap on, adjust swappiness for low RAM system.

sudo fallocate -l 4G /swapfile && \
sudo chmod 600 /swapfile && \
sudo mkswap /swapfile && \
sudo swapon /swapfile && \
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab && \
sudo sysctl vm.swappiness=5 && \
echo 'vm.swappiness=5' | sudo tee -a /etc/sysctl.conf && \
sudo apt update -y && sudo apt upgrade -y && sudo apt autoremove -y && sudo apt install build-essential git micro ufw -y

§Migrate firewall to UFW

UFW has a simple and easy to use interface, and it's my preference for configuring firewall inside a Linux system, though these commands below are easily adaptable to other systems.

A common beginner mishap is improperly migrating to a different firewall system and blocking yourself out of your VPS by disallowing foreign connections (including your own connection). To mitigate this, directly copy-pasting the below command so every command runs sequentially is advised. (see: sudo ufw limit ssh)

sudo apt remove --purge firewalld iptables-persistent netfilter-persistent -y && \
sudo ufw limit ssh && \
sudo ufw allow 80,443/tcp && \
sudo ufw allow 80,443/udp && \
sudo iptables -P INPUT ACCEPT && \
sudo iptables -P FORWARD ACCEPT && \
sudo iptables -P OUTPUT ACCEPT && \
sudo iptables -F && \
sudo iptables -X && \
sudo ip6tables -F && \
sudo ip6tables -X && \
sudo ufw --force enable && \
sudo ufw status verbose
  • To delete a rule, you can run sudo ufw delete allow 80,443/tcp

§Disable plaintext password SSH connection attempts

Don't set up an easy password thinking nobody would bother touching your site. All public websites get malicious traffic, and you have to expect and defend against them. Disabling plaintext password makes it so you can only enable an SSH connection to your VPS

sudo micro /etc/ssh/sshd_config
# make sure these parameters are set as such:
# PasswordAuthentication no
sudo sshd -t
sudo systemctl restart ssh

§Set up Git

When setting up git, there are these 6 - 7 commands that I have to look up whenever I'm in a fresh environment, so here they are.

ssh-keygen -t ed25519 && \
git config --global gpg.format ssh && \
git config --global user.signingkey "~/.ssh/id_ed25519.pub" && \
git config --global commit.gpgsign true && \
git config --global user.email "149798217+onuralp-t@users.noreply.github.com" && \
git config --global user.name "onuralp-t" && \
echo "$(git config --global user.email) $(cat ~/.ssh/id_ed25519.pub)" >> ~/.ssh/allowed_signers

§Optional: pretty prompt

I like pretty prompts, and default bash prompt is pretty ugly and unergonomic for non-experts. I tried zsh and fish but didn't like them much. So I decided to just prettify the existing bash setup and add some functionality. This is a basic setup that I like:

sudo apt install -y fzf bash-completion && \
curl -sS https://starship.rs/install.sh | sh

cat << 'EOF' > ~/.inputrc
set completion-ignore-case On
set show-all-if-ambiguous On
set completion-map-case On
set colored-stats On
TAB: menu-complete
# Shift-Tab to cycle backwards
"\e[Z": menu-complete-backward
EOF

cat << 'EOF' > ~/.config/starship.toml
add_newline = false
[line_break]
disabled = true

[character]
success_symbol = "[❯](bold green)"
error_symbol = "[❯](bold red)"

[directory]
truncation_length = 3
truncate_to_repo = true
style = "bold cyan"

[git_branch]
format = "[$branch]($style) "
style = "bold purple"

[git_status]
format = '([$all_status$ahead_behind]($style) )'
style = "red"
EOF

cat << 'EOF' > ~/.bashrc
# If not running interactively, don't do anything
[[ $- != *i* ]] && return

alias ls='ls --color=auto'
alias grep='grep --color=auto'

if [ -f /etc/bash_completion ]; then
    . /etc/bash_completion
elif [ -f /usr/share/bash-completion/bash_completion ]; then
    . /usr/share/bash-completion/bash_completion
fi

if command -v fzf &>/dev/null; then
    eval "$(fzf --bash)"
fi

eval "$(starship init bash)"
EOF
